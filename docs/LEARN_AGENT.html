Pass 1: tracing one question end to end

Question traced: Compare LA and Santa Ana airport congestion levels. Where this guide shows data, it says whether it is a logged real model run, a real tool run on the committed snapshot, or a shape built by the repo's own code. Nothing is invented. Unverified is stated where it applies.

What was and was not run. I did not make a new live model call (it costs money and you asked me to ask first). The model's tool choices and its final answer come from the logged eval run 4 transcript of this exact question. The tool results are re-generated by running the real tool code on the committed snapshot; they match the table in the logged answer (for example LAX 25,062 passengers per runway per day, load factor 82.1%, SNA score 73.9). Unverified: that the two searches were sent in one model turn (the transcript lists tool calls in order but not the turn boundaries), the tool-call ids, the token counts and the latency of this single conversation.

The flow, CODE vs MODEL

CODEBrowser sends the message
api/static/index.html: fetch POST /chat with session_id and message
↓
CODEFastAPI validates and starts the turn
ChatRequest (length limits) then Agent.run_turn; a session id is created if the client has none
↓
CODEAgent loads the session history
MemorySessionStore.get_or_create; first message, so the history is empty
↓
MODELModel call 1: what do I need?
Receives system prompt + 8 tool definitions + the question. Decides to call search_airports for "LA" and for "Santa Ana"
↓
CODETools run (in parallel)
Validate arguments, search_airports over the airport list, return matches (LAX first for "LA"; SNA for "Santa Ana")
↓
MODELModel call 2: pick the airports, call the comparison
Sees both results. Chooses LAX and SNA and calls compare_airports
↓
CODEcompare_airports computes everything
KPIs, per-runway ratios, points per component, leaders, differences, caveats: all deterministic
↓
MODELModel call 3: write the answer
Sees the comparison JSON. No more tool calls, so this text is the final reply
↓
CODEAgent saves history, logs the turn, API returns JSON; page shows it
Session saved; a turn log line records tools, latency and tokens

Three model calls and three tool calls (two of them in parallel, if the searches shared a turn). The MODEL steps decide what to ask for and how to say it; every number in the answer was produced in the CODE steps.

Agent engineering concepts

Agent engineering concept: the tool-calling loop

An LLM cannot call your code. It can only emit text. A tool-calling loop gives it a menu of functions (names, descriptions, JSON schemas); the model replies either with a final answer or with a request "call function X with these arguments"; your code runs it, appends the result to the conversation, and calls the model again. Repeat until the model answers without a tool request.

Backend analogy. An orchestrator or saga where the next step is chosen at run time by a remote, non-deterministic service instead of an if/else. Your code is the executor and the guard; the model is the planner.

In this project. The loop is core/agent.py:97. The model chose 3 tool calls here and could have chosen different ones.

In production. The same loop, plus streaming output, per-user budgets (tokens, tool calls), and an audit trail of every tool call.

Agent engineering concept: how tool schemas reach the model

Each tool is described to the model as a name, a natural-language description and a JSON Schema for its arguments. The model decides when to call it from the description and builds the arguments from the schema. The description is effectively part of the prompt.

Backend analogy. An OpenAPI document that the caller reads at run time. The Pydantic model is the request DTO and also generates the schema, so validation and documentation cannot drift apart (like Swagger generated from a Spring controller or an ASP.NET model).

In this project. core/tools.py:33 turns a Pydantic model into the schema with model_json_schema(). The same class validates the arguments when they come back (core/tools.py:76).

In production. Tool descriptions get reviewed and versioned like code, because changing one changes behaviour. (Candidate change #1 is an example of a description that drifted from the data.)

Agent engineering concept: why tool results go back as a user message

Anthropic's Messages API only has two roles, user and assistant. A tool request is a tool_use block inside an assistant message; its result is a tool_result block inside the next user message, linked by tool_use_id. The model must see its own request followed by the matching result. Other providers use a separate tool role; the repo keeps its own provider-neutral Message type and translates in the adapter.

Backend analogy. Like correlation ids in a request/reply messaging pattern (Kafka request-reply): the reply carries the id of the request it answers.

In this project. adapters/anthropic_llm.py:75 does the translation. The model class is core/interfaces.py:34.

In production. Unchanged. If another provider were added, only a second adapter would be written.

Agent engineering concept: stop_reason

Every model reply says why it stopped: it finished its answer (end_turn), wants a tool (tool_use), hit the token limit (max_tokens), and so on. A loop can branch on it.

Backend analogy. Like an HTTP status code on the response.

In this project. This loop does not branch on it; it checks whether the reply contains tool calls (core/agent.py:104). The adapter logs it on every call (adapters/anthropic_llm.py:47) and warns on max_tokens (adapters/anthropic_llm.py:51). A weakness: a reply cut off by max_tokens in the middle of a tool call is not treated as an error (candidate change #2).

In production. Alert on the rate of max_tokens stops; treat them as failures when they cut a tool call.

Agent engineering concept: why the model never does arithmetic here

Language models write plausible numbers; they do not compute reliably. The design rule is: numbers come from code, words come from the model.

Backend analogy. Like never letting the UI compute an invoice total: the service computes it, the UI only displays it.

In this project. Ratios, differences, points, leaders and the as-of date all come from the tool result. The system prompt forbids calculating (domain/system_prompt.md rule 1), and the evals include a number audit that fails any number not found in a tool result.

In production. Same, plus monitoring: sample live answers and check numbers against tool results. Also known: the audit cannot tell a wrong number that equals another value in the result.

Agent engineering concept: prompt caching

Each model call resends the system prompt, the tool definitions and the whole history. The provider can keep the unchanged beginning of the request in a cache and charge much less (and answer faster) when the next call starts with the same text.

Backend analogy. Like caching a stable prefix: the cache key is the request prefix, so editing the system prompt or a tool description invalidates it.

In this project. One parameter, adapters/anthropic_llm.py:35. Measured: in eval run 4, 265,330 of 551,644 input tokens were read from the cache (docs/EVALS.md). Default cache lifetime is short (minutes); the exact value is unverified here.

In production. Keep the prefix stable (no timestamps in the system prompt), watch the cache-hit rate on the dashboard, and put volatile text last.

Agent engineering concept: parallel tool calls

A model can request several independent tools in one turn. If your code runs them one after another, the user waits for the sum; run them together and they wait for the slowest.

Backend analogy. Task.WhenAll in .NET, CompletableFuture.allOf in Java, Promise.all in JS.

In this project. core/agent.py:144. Here the two searches are independent (assumed to share a turn; unverified). The compare call depends on both, so it comes in the next round.

In production. Same, with a concurrency limit per user, so one chat cannot open 20 simultaneous calls to a client's backend.

Agent engineering concept: deterministic vs LLM parts

Split every feature into the part that must be repeatable and checkable (data, scoring, validation, errors) and the part that needs language (understanding the question, choosing tools, explaining). Give the model only the second.

Backend analogy. Like keeping business rules in the domain service and letting a template engine do the wording.

In this project. MODEL: which tool, which airport codes, how to phrase the answer. CODE: everything else. The same ranking is also served with no model at GET /ranking.

In production. The line between them is what you can test, version and audit; keep it this crisp.

Agent engineering concept: hallucination control (first part)

A model hallucinates when it states things it was not given. Controls: do not give it calculations to do, give it the facts and caveats, tell it what to say when data is missing, and test for violations.

Backend analogy. Like validating at every boundary rather than trusting the caller.

In this project. Numbers from tools; caveats attached by code (domain/config.yaml); "not measured" wording in the prompt; evals that check it. Pass 4 covers the number audit and the judge.

In production. Add online sampling and a regression set built from real bad answers.

Concepts coming in later passes: max iterations and timeouts (pass 3), evals vs unit tests and LLM-as-judge (pass 4), percentiles and weights (pass 2).

Interview questions: pass 1

Q1. Why did you write the agent loop yourself instead of using LangChain or another framework?

The loop is about 190 lines and I can explain every branch: the iteration cap, the retry, the parallel tools, what is saved on failure. A framework would hide those behaviours, and they are the reliability questions an enterprise asks. The cost is that I own bugs a library would have fixed.

Point at: core/agent.py:97

Q2. Why no RAG?

There is no document collection to search: the knowledge the agent needs is a few definitions and caveats, which live in config and are returned by get_methodology. The facts that matter are structured numbers, which come from queries, not from text retrieval. If the client had master plans or FAA reports, I would add retrieval for those documents only.

Point at: domain/analytics.py:553

Q3. Why no MCP?

The tools run in the same process as the agent, so MCP would add a network hop and a server to run for no benefit today. The tools are plain functions with schemas, so exposing them over MCP later is a thin wrapper if another client, like a desktop assistant, needs the same tools.

Point at: domain/tools.py:54

Q4. Why Postgres when you load a snapshot of CSV files?

In a real engagement the backend is a database or an API, so the code goes through a repository interface and Postgres is the realistic implementation; the in-memory one runs tests, evals and the CLI. The snapshot means no external API on the request path. If the data were this small and static forever, flat files would be enough, and I say so in DECISIONS.md.

Point at: domain/repository.py:51

Q5. Why eight narrow tools instead of one "run SQL" tool?

Narrow tools let code guarantee the numbers, validate inputs and attach caveats; free SQL would let the model invent its own calculation and read any table. Narrow tools also make evals simple: I can assert which tool was called with which arguments.

Point at: domain/tools.py:54

Q6. How does the model know which tools exist and how to call them?

Every call sends the tool definitions: name, description and a JSON schema generated from the Pydantic argument class. The model picks a tool from the description and fills in arguments from the schema; my code validates them again before running.

Point at: core/tools.py:33

Q7. Why do tool results go back to the model instead of straight to the user?

The model has to turn data into an explanation and decide whether it needs another tool, as it did here: search first, then compare. The result is appended as a tool_result block in the next user message, linked to the request by an id.

Point at: core/agent.py:111

Q8. What stops the model from making up the 25,062 number?

Three layers: it never has to compute it, because compare_airports returns it; the prompt forbids calculating; and the evals include a number audit that fails any number in an answer that is not in a tool result. It is not a proof: the audit cannot catch a wrong number that happens to equal another value in the result.

Point at: domain/analytics.py:404

Q9. Why async, and why gather?

Model and tool calls are slow I/O, so one process can serve many chats while they wait. gather makes independent tool calls run together, so a two-airport lookup costs the slowest call, not the sum. For a voice agent that matters.

Point at: core/agent.py:144

Q10. What happens on the first request after a restart, and is that a problem?

The first tool call builds the national KPI table for all 228 airports under a lock, then every later call reuses it. It adds a short delay once per process; I have not measured it here (unverified). In production I would warm it at startup or on a health check.

Point at: domain/analytics.py:76
