Pass 1: tracing one question end to end

Question traced: Compare LA and Santa Ana airport congestion levels. Where this guide shows data, it says whether it is a logged real model run, a real tool run on the committed snapshot, or a shape built by the repo's own code. Nothing is invented. Unverified is stated where it applies.

What was and was not run. I did not make a new live model call (it costs money and you asked me to ask first). The model's tool choices and its final answer come from the logged eval run 4 transcript of this exact question. The tool results are re-generated by running the real tool code on the committed snapshot; they match the table in the logged answer (for example LAX 25,062 passengers per runway per day, load factor 82.1%, SNA score 73.9). Unverified: that the two searches were sent in one model turn (the transcript lists tool calls in order but not the turn boundaries), the tool-call ids, the token counts and the latency of this single conversation.

The flow, CODE vs MODEL

CODEBrowser sends the message
api/static/index.html: fetch POST /chat with session_id and message
↓
CODEFastAPI validates and starts the turn
ChatRequest (length limits) then Agent.run_turn; a session id is created if the client has none
↓
CODEAgent loads the session history
SessionStore.get_or_create (a Postgres row in the API); first message, so the history is empty
↓
MODELModel call 1: what do I need?
Receives system prompt + 8 tool definitions + the question. Decides to call search_airports for "LA" and for "Santa Ana"
↓
CODETools run (in parallel)
Validate arguments, search_airports over the airport list, return matches (LAX first for "LA"; SNA for "Santa Ana")
↓
MODELModel call 2: pick the airports, call the comparison
Sees both results. Chooses LAX and SNA and calls compare_airports
↓
CODEcompare_airports computes everything
KPIs, per-runway ratios, points per component, leaders, differences, caveats: all deterministic
↓
MODELModel call 3: write the answer
Sees the comparison JSON. No more tool calls, so this text is the final reply
↓
CODEAgent saves history, logs the turn, API returns JSON; page shows it
Session saved; a turn log line records tools, latency and tokens

Three model calls and three tool calls (two of them in parallel, if the searches shared a turn). The MODEL steps decide what to ask for and how to say it; every number in the answer was produced in the CODE steps.

Things that were confusing while reading _loop, answered once here.

"assistant" is the model, not a helper for the model

The API labels each message with who said it. user is the outside world: the human, or our code passing something in. assistant is the model itself, the same naming as in any chat app (you are the user, the AI is the assistant). So Message(role="assistant", tool_calls=...) is a recording of what the model said: "I want to call these tools". The model chose the tools; our code only writes the choice down and then runs them.

RoleWho is speakingExample in this question
userthe human"Compare LA and Santa Ana airport congestion levels."
assistantthe model"call search_airports(LA) and (Santa Ana)", later "call compare_airports(LAX, SNA)", finally the answer text
userour code, answering for the toolsthe tool results (tool_result blocks)

The two appends in the loop

The model has no memory between calls, so the code keeps the whole conversation as a list and resends it every time. After a model reply that asks for tools, the loop appends two things:

  1. Message(role="assistant", ..., tool_calls=response.tool_calls): what the model asked for.
  2. Our code runs the tools, then Message(role="user", tool_results=results): the answers, each carrying the id of the request it answers (like a correlation id in Kafka request-reply).

The API requires every tool request to be followed directly by its matching results. This is also why run_turn keeps this turn's messages in new_messages and saves them to the session only at the end: a failed turn would otherwise leave a request without its result in the stored history.

What the 6 limits

for _ in range(self._max_iterations) runs up to 6 times, and each pass makes one model call. The cap counts model calls, not tool calls. In one round the model can ask for several tools at once and they run in parallel.

RoundModel callWhat it does (example question)
1call 1asks for 2 searches (parallel)
2call 2asks for compare_airports
3call 3writes the final answer, so the loop returns
  • The answering call must happen within the 6. In practice that is at most 5 rounds of tool use and then the answer.
  • If the model asks for tools again in round 6, the code still runs them, then the loop ends, logs max_iterations_reached and returns None, which becomes the fallback reply. The results of those last tools are never used (a harmless inefficiency; pass 3 covers this path).
  • The cap is a circuit breaker against a model that keeps asking for tools (for example retrying a failing tool forever). The value comes from max_iterations in app/settings.py.

How the loop decides to stop

If the reply has no tool requests, its text is the final answer (if not response.tool_calls). Otherwise the tools run and the loop continues. A reply can contain text and tool requests together (for example a short preamble); the code only looks at whether tool requests exist, so that text is stored in the history but never shown to the user. "Enough data to answer" is the model's own judgment, shaped by the system prompt (rule 8: call the tools again for a new airport instead of guessing; rule 9: retry a failing tool once, then say so). Nothing in the code checks that the data is sufficient; the 6-round cap is the safety net.

Agent engineering concepts

Agent engineering concept: the tool-calling loop

An LLM cannot call your code. It can only emit text. A tool-calling loop gives it a menu of functions (names, descriptions, JSON schemas); the model replies either with a final answer or with a request "call function X with these arguments"; your code runs it, appends the result to the conversation, and calls the model again. Repeat until the model answers without a tool request.

Backend analogy. An orchestrator or saga where the next step is chosen at run time by a remote, non-deterministic service instead of an if/else. Your code is the executor and the guard; the model is the planner.

In this project. The loop is core/agent.py:99. The model chose 3 tool calls here and could have chosen different ones.

In production. The same loop, plus streaming output, per-user budgets (tokens, tool calls), and an audit trail of every tool call.

Agent engineering concept: how tool schemas reach the model

Each tool is described to the model as a name, a natural-language description and a JSON Schema for its arguments. The model decides when to call it from the description and builds the arguments from the schema. The description is effectively part of the prompt.

Backend analogy. An OpenAPI document that the caller reads at run time. The Pydantic model is the request DTO and also generates the schema, so validation and documentation cannot drift apart (like Swagger generated from a Spring controller or an ASP.NET model).

In this project. core/tools.py:33 turns a Pydantic model into the schema with model_json_schema(). The same class validates the arguments when they come back (core/tools.py:76).

In production. Tool descriptions get reviewed and versioned like code, because changing one changes behaviour. (Candidate change #1 is an example of a description that drifted from the data.)

Agent engineering concept: why tool results go back as a user message

Anthropic's Messages API only has two roles, user and assistant. A tool request is a tool_use block inside an assistant message; its result is a tool_result block inside the next user message, linked by tool_use_id. The model must see its own request followed by the matching result. Other providers use a separate tool role; the repo keeps its own provider-neutral Message type and translates in the adapter.

Backend analogy. Like correlation ids in a request/reply messaging pattern (Kafka request-reply): the reply carries the id of the request it answers.

In this project. adapters/anthropic_llm.py:92 does the translation. The model class is core/interfaces.py:34.

In production. Unchanged. If another provider were added, only a second adapter would be written.

Agent engineering concept: stop_reason

Every model reply says why it stopped: it finished its answer (end_turn), wants a tool (tool_use), hit the token limit (max_tokens), and so on. A loop can branch on it.

Backend analogy. Like an HTTP status code on the response.

In this project. This loop does not branch on it; it checks whether the reply contains tool calls (core/agent.py:106). The adapter logs it on every call (adapters/anthropic_llm.py:51) and warns on max_tokens (adapters/anthropic_llm.py:55). A weakness: a reply cut off by max_tokens in the middle of a tool call is not treated as an error (candidate change #2).

In production. Alert on the rate of max_tokens stops; treat them as failures when they cut a tool call.

Agent engineering concept: why the model never does arithmetic here

Language models write plausible numbers; they do not compute reliably. The design rule is: numbers come from code, words come from the model.

Backend analogy. Like never letting the UI compute an invoice total: the service computes it, the UI only displays it.

In this project. Ratios, differences, points, leaders and the as-of date all come from the tool result. The system prompt forbids calculating (domain/system_prompt.md rule 1), and the evals include a number audit that fails any number not found in a tool result.

In production. Same, plus monitoring: sample live answers and check numbers against tool results. Also known: the audit cannot tell a wrong number that equals another value in the result.

Agent engineering concept: prompt caching

Each model call resends the system prompt, the tool definitions and the whole history. The provider can keep the unchanged beginning of the request in a cache and charge much less (and answer faster) when the next call starts with the same text.

Backend analogy. Like caching a stable prefix: the cache key is the request prefix, so editing the system prompt or a tool description invalidates it.

In this project. One parameter, adapters/anthropic_llm.py:39. Measured: in eval run 4, 265,330 of 551,644 input tokens were read from the cache (docs/EVALS.md). Default cache lifetime is short (minutes); the exact value is unverified here.

In production. Keep the prefix stable (no timestamps in the system prompt), watch the cache-hit rate on the dashboard, and put volatile text last.

Agent engineering concept: parallel tool calls

A model can request several independent tools in one turn. If your code runs them one after another, the user waits for the sum; run them together and they wait for the slowest.

Backend analogy. Task.WhenAll in .NET, CompletableFuture.allOf in Java, Promise.all in JS.

In this project. core/agent.py:150. Here the two searches are independent (assumed to share a turn; unverified). The compare call depends on both, so it comes in the next round.

In production. Same, with a concurrency limit per user, so one chat cannot open 20 simultaneous calls to a client's backend.

Agent engineering concept: deterministic vs LLM parts

Split every feature into the part that must be repeatable and checkable (data, scoring, validation, errors) and the part that needs language (understanding the question, choosing tools, explaining). Give the model only the second.

Backend analogy. Like keeping business rules in the domain service and letting a template engine do the wording.

Agent engineering concepts

Agent engineering concept: deterministic scoring beside an LLM (and why not let the model rank)

A model asked to rank airports from raw tables would give different, unreproducible answers and could not show its arithmetic. Scoring is therefore ordinary code the model calls as a tool: same input, same output, and an analyst can reproduce every number.

Backend analogy. A pricing or risk engine behind a service: the chatbot in front of it explains the quote but never computes it.

Agent engineering concepts

Agent engineering concept: timeouts, retries and backoff

Every network call needs a deadline and a bounded retry policy, or one slow dependency hangs the whole conversation. Retry only failures that can pass on a second try (timeouts, rate limits, 5xx), wait between attempts, and stop.

Backend analogy. Polly (.NET) or Resilience4j (Java) policies: timeout, retry with exponential backoff.

In this project. Model: 30 s timeout, one retry, 0.5 s backoff (core/agent.py:132). Tools: 10 s timeout, one retry, 0.2 s backoff (core/tools.py:86). Fatal errors are not retried.

In production. Add jitter and honour the provider's Retry-After header on 429, a circuit breaker so a dead provider fails fast, and a fallback model or second provider.

Agent engineering concept: errors are data, not exceptions, inside the loop

When a tool fails, the model is better off knowing: it can retry once, choose another tool, or tell the user. So failures become structured results ({error: {code, message}}) rather than exceptions that end the conversation.

Backend analogy. An API returning a problem-details body instead of crashing the caller.

In this project. core/tools.py:49: expected errors keep their message, unexpected ones become a generic internal_error so internals are not leaked to the model.

In production. Same, plus alerting on the rate of tool errors per tool, taken from the tool_call log lines.

Agent engineering concept: runaway-loop protection (max iterations)

A model that keeps asking for tools can loop indefinitely and burn money. A hard cap on model calls per turn is the simplest guard.

Backend analogy. A circuit breaker or a retry limit; also a recursion depth limit.

In this project. 6 model calls (core/agent.py:103), then the fallback reply. Candidate changes: do not run tools on the last allowed call, and give a more specific message.

In production. Add a per-turn token budget and a total turn deadline, and track how often the cap is hit.

Agent engineering concept: atomic turns: never store half a conversation

A tool request without its matching result is an invalid history for the provider. If a turn fails midway, saving the partial history would make every later message fail too.

Backend analogy. A transaction: commit only when everything succeeded, otherwise roll back.

In this project. New messages are collected apart and saved only at the end (core/agent.py:96). The cost: a failed turn leaves no trace of the user's question.

In production. Same. If transcripts are needed for audit, store failed turns separately and mark them failed.

Agent engineering concept: fail closed: do not let the model invent data when tools fail

The dangerous failure is not the error, it is a confident answer built from memory. The model must be told what to do, and tests must check it.

Backend analogy. Returning 503 rather than a stale or made-up value.

In this project. The tool error text says "Do not guess the data"; prompt rule 9 says retry once, then say so, and do not name airports or give examples from memory; the eval case backend_outage fails any answer that names airports while the tools are down (it passed 3 of 3).

In production. Add online checks that sample answers produced during incidents.

Interview questions: pass 3

Q1. What happens if the model provider times out?

Each attempt has a 30 second limit. On a timeout the agent waits half a second and retries once. If that also fails, it logs the error with the traceback and the user gets a short apology with failed=true. Nothing is saved for that turn, so the conversation stays valid.

Point at: core/agent.py:127

Q2. Why retry only once, and why back off?

A second attempt fixes most transient problems like a dropped connection or a brief 5xx. More retries multiply the wait for a user who is already waiting. The backoff gives an overloaded service a moment, though I have no jitter yet.

Point at: core/agent.py:144

Q3. Why do tool errors go to the model instead of raising?

The model can use them: retry once, try another tool or tell the user plainly. If they raised, one bad tool call would end the whole conversation. execute never raises, which also means one failing tool in a parallel batch cannot break the others.

Point at: core/tools.py:49

Q4. A tool crashes. How do you stop the model making up the answer?

Three things: the error text tells it not to guess, the prompt says retry once then tell the user and do not name airports or examples from memory, and an eval case with a broken backend fails any answer that names an airport. It passed 3 of 3 runs, but it is a check, not a proof.

Point at: core/tools.py:61

Q5. Is retrying a tool safe?

Yes here, because every tool is read-only, so repeating it changes nothing. A write tool would need an idempotency key so a retry cannot create a duplicate.

Point at: core/tools.py:81

Q6. What stops the loop running forever, and what is the worst-case wait?

A cap of 6 model calls per turn, plus timeouts and one retry on every call. With the production values the theoretical worst case adds up to about 8 minutes, because there is no total deadline for the turn. Real turns averaged 5.7 seconds in the last eval. I would add a turn-level timeout, especially for voice.

Point at: core/agent.py:103

Q7. What is saved when a turn fails?

Nothing. The turn's messages are kept in a separate list and appended to the session only on success, because a tool request without its result would make the history invalid for the provider. The downside is that the failed question is not remembered.

Point at: core/agent.py:89

Q8. What does a user see if the API key is wrong?

A specific message, "The Anthropic API key was rejected. Check ANTHROPIC_API_KEY in .env.", returned at once because a rejected key, an unknown model or any other 4xx is not retried. The real provider error stays in the logs.

Point at: core/agent.py:84

Q9. How would you make this safer in production?

A circuit breaker and a fallback model for provider outages, jitter and Retry-After on retries, a total deadline per turn, a token budget, and alerts on the rate of llm_failed, tool errors and max_iterations_reached, which are already separate log events.

Agent engineering concepts

Agent engineering concept: evals versus unit tests

A unit test checks code with a fixed input and an exact expected output. An eval checks a system whose output varies run to run, so it checks properties (right tool called, no invented number, admits a limit) over many cases and reports a rate.

Backend analogy. Unit tests are your usual tests; evals are closer to contract tests plus a canary that tells you whether a change made the product better or worse.

In this project. Unit tests (294) cover the scoring math, the loop, the tools and the checks themselves with fixed inputs, and need no network. The evals (evals/runner.py:287) call the live model and are the only code that does besides the app.

In production. Run the evals in CI before every release (a gate on prompt, model and tool changes) and track the same metrics online.

Agent engineering concept: deterministic checks first, LLM judge for the rest

Anything a rule can decide should be a rule: it is free, repeatable and explainable. Use a model judge only for what rules cannot see, such as whether a sentence is supported by the evidence.

Backend analogy. Assertions before a human review: automate the cheap objective checks, keep expensive subjective review for what is left.

In this project. evals/runner.py:177 first; the judge only where a case sets judge_grounded (evals/runner.py:301).

In production. Calibrate the judge against human labels on a sample, use a different model family as judge, and re-check it whenever the model changes.

Agent engineering concept: LLM-as-judge: rubric, noise, majority vote, fail closed

A judge needs a fixed rubric, sees only the evidence, returns a structured verdict, and is treated as noisy: one call can pass what the next call fails. Voting reduces noise; an unreadable verdict must count as a failure.

Backend analogy. A flaky test: if it is not deterministic you either fix the source of noise or repeat it and take the majority.

In this project. Three calls, majority decides, disagreement reported, garbled output fails closed. In run 4 the three calls disagreed on 3 of 19 answers.

In production. Add a second judge model, temperature 0 where the API allows it, and a periodic human audit of judge decisions.

Agent engineering concept: the number audit (hallucination control, part 2)

To make "numbers come from code" testable, extract every number from the answer and require each to appear in a tool result (allowing real rounding), the user's message or the config.

Backend analogy. A checksum on the output: cheap, strict, and it catches the commonest failure.

In this project. evals/number_audit.py:121; it runs on every case. It cannot tell a wrong number from a coincidence, and it only runs in evals.

In production. Run it on a sample of live answers and alert on failures.

Agent engineering concept: safety cases repeated, and the noise lesson

A model can pass once by luck. Cases that must never fail run several times and must pass every time. And with a small sample, a change of one or two cases is noise, not progress.

Backend analogy. Running a flaky integration test 3 times before trusting it.

Architecture in 5 lines

  1. Ingest (make ingest) builds a committed snapshot (BTS T-100 traffic, OurAirports runways) that is loaded into Postgres at startup; the FAA feed is the only live call.
  2. Scoring is pure code (domain/scoring.py, analytics.py): KPIs, national percentiles, weighted sum; no model.
  3. Eight read-only tools wrap the analytics; arguments are validated, errors are structured results.
  4. The agent loop (core/agent.py) lets Claude choose tools and write the answer: max 6 model calls, timeouts, one retry, sessions in Postgres.
  5. Chat UI and API (FastAPI): POST /chat, GET /ranking (no model), /docs; evals and unit tests guard it.

The score formula

Expansion Pressure Score (0 to 100) = 0.25 x growth + 0.25 x load factor + 0.20 x passengers per commercial runway + 0.15 x demand gap + 0.10 x scale + 0.05 x peak ratio, each term being the mid-rank percentile (0 to 100) of that measure against the 228 peers, over the last 12 months (May 2025 to Apr 2026) versus the 12 before. Commercial runway = open, paved, at least 5,000 ft. An airport with any missing input is not scored. Relative, judgmental, not capacity, not profit.

Top 10 interview questions

  1. Why no agent framework?
    The loop is one 187-line file I can explain fully: the cap, the retry, parallel tools, timeouts, what is saved on failure. A framework would hide exactly what reliability questions are about.
  2. How do you know the model isn't making numbers up?
    It never computes them: tools return finished figures from deterministic code, the prompt forbids calculating, and the evals run a number audit that fails any number not in a tool result. It is a strong check, not a proof, and it runs in evals, not live.
  3. What does the score mean?
    Demand pressure relative to 228 peers on six weighted percentiles. Not terminal capacity, not profit, not absolute strain.
  4. Why percentiles, and why these weights?
    Percentiles put unlike units on one scale without arbitrary bounds. Weights are judgment, adjustable in chat, and I show how the top five moves; they are not fitted because I have no expansion history.
  5. How do you answer the long-haul share at Anchorage?
    I don't invent it: route-level data isn't public through the APIs I tested, so I give two labelled proxies (international share of departures, average distance) and say why they are rough.
  6. What happens when the model or a tool fails?
    One retry, then a fallback reply; tool errors go to the model as structured results; a cap of 6 model calls; failed turns are not saved. Known gap: no total deadline per turn.
  7. How are the evals set up, and is 75% good?
    20 cases, rules first and a three-vote judge for groundedness, 11 safety cases run three times. 75% is a measuring tool improving, within the noise I measured, with no unsafe answer and every failure documented.
  8. Why a snapshot and Postgres?
    No external API on the request path, so answers are fast and reproducible. Postgres is the realistic backend behind a repository interface; in-memory runs the tests.
  9. What would production need?
    Redis for live sessions plus Postgres for transcripts, auth and per-user session ownership, a turn deadline, circuit breaker and fallback model, tracing, CI eval gate, scheduled ingest.
  10. Where is AI used and where not?
    The model resolves names, chooses tools and writes the explanation. Code computes every number, ranking and explanation fact. That line is what makes it testable and auditable.

Known limits and what to say

  • Evals: 15 of 20 (75%) in run 4; no unsafe answer; two safety cases at 2 of 3 from an audit false positive and a judge that cannot see the system prompt; judge is the same model; non-safety cases run once.

Concepts

Agent engineering concept: conversation state lives on the server, keyed by an id

The model is stateless: each call needs the full history. Something has to remember it between the user's messages. Either the client resends everything, or the server stores it and the client sends only an id. This project does the second, so the browser cannot edit the history (including tool results) and requests stay small.

Backend analogy. A session table keyed by a session token, like server-side HTTP sessions, except the "session" is a list of messages.

In this project. core/agent.py:79 loads, core/agent.py:96 saves; the id comes from api/main.py:90.

In production. The id is bound to an authenticated user, and history is stored per user with a retention limit.

Agent engineering concept: why Postgres here, Redis plus Postgres in production

Live session state is read and written on every turn and can expire; a transcript is a record you may have to keep for audit, review and evals. Those are different needs.

Backend analogy. Redis with a TTL is a session cache (like ASP.NET distributed session or Spring Session); Postgres is the system of record (like an audit table fed from Kafka).

In this project. One database for both, because Postgres is already running and adding Redis would be a new service for a one-day build.

In production. Redis with a TTL for the live state, Postgres for permanent transcripts and the audit log. The interface stays; only the adapters change (documented in DECISIONS.md, not built).

Agent engineering concept: lost update (last write wins)

Two requests on the same session at once both read the same history, each adds its own turn, and the later save overwrites the earlier one, so one turn disappears.

Backend analogy. The classic lost update, fixed in JPA with @Version, in EF with a rowversion, in HTTP with ETag and If-Match.

In this project. Not handled: the upsert replaces the row. It is rare for one chat user (a double click) but real.

In production. A per-session lock (advisory lock or Redis lock) or a version column checked in the UPDATE, retrying or rejecting on a mismatch.

Agent engineering concept: history growth

The history includes every tool result in full, and every model call resends it. Long conversations cost more tokens and time, and the row is rewritten whole on each turn.

Backend analogy. Like an unbounded list field on an aggregate: it needs a size cap or archiving.

In this project. Not handled; documented as next step. Prompt caching softens the cost of the repeated prefix.

In production. Keep the last N turns or summarize older ones, and store tool results by reference when they are large.

Interview questions: session state

Q1. Where does the conversation state live, and why is the API stateless?

The model remembers nothing, so the server keeps each conversation as a list of messages in a Postgres row keyed by session id. The API process holds no state, so a restart loses nothing and a second replica can serve any session. The page only holds the id.

Point at: adapters/postgres_session_store.py:23

Q2. What happens if two requests hit the same session at once?

Both load the same history and the second save overwrites the first, so one turn is lost: last write wins. It is rare for one chat user, so I documented it rather than building it. The fix is a per-session lock or a version column checked on save.

Point at: adapters/postgres_session_store.py:11

Q3. Why one JSONB row per session instead of a messages table?

Nothing queries individual messages, the whole history is read and written together, and one row keeps the code to two small functions. A messages table becomes worth it when you need to search or report across messages, or when histories get large enough that rewriting the row hurts.

Postgres was already running, so it adds no service and gives durability. Live session state is hot and can expire, which suits Redis with a TTL, while transcripts must be kept for audit and evals, which suits Postgres. Because the loop depends only on the SessionStore interface, only the adapters change.
