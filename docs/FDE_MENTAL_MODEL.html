Being an AI software engineer and a forward deployed engineer

A mental model for the interview. It starts with what an agent really is, goes through the five things that make up the real engineering work, and ends with the FDE role and an interview kit. Every idea is tied to the project in this repo, so you can point at real code.

The mental model in one page

An AI agent is a language model running in a loop, with tools it can request and state it can remember. The loop is small. Almost all of the engineering is everything around it.

What the model actually is

Start from the right picture of the model, because every design decision follows from it. A language model, from your code's point of view, is a function. You give it text (a system prompt, the conversation so far, and descriptions of the tools it may use). It gives you back text, or a request to use a tool. That is all.

  • It is stateless. It remembers nothing between calls. If it "remembers" your name, it is because your code sent the earlier messages again.
  • It is not deterministic. The same input can produce different outputs. You cannot test it like a normal function with one expected answer.
  • It can be confidently wrong. It writes plausible text. It does not know when it is making something up.
  • It follows instructions, but not like a program. A prompt is a strong suggestion, not a guarantee. A cleverly worded user message can change its behavior.
  • Cost and speed depend on how much text goes in and out. Longer prompts and longer answers cost more and take longer.

The whole discipline of building agents is: take a component that is stateless, non-deterministic, sometimes wrong and persuadable, and build a system around it that is reliable, safe and measurable enough to put in front of a bank's customers.

The loop is about ten lines

messages = history + [user_message]
for step in range(MAX_STEPS):                       # a hard cap, so it cannot loop forever
    reply = llm(system_prompt, messages, tools)     # 1. ask the model
    if not reply.tool_calls:
        return reply.text                           # 2. it answered: done
    messages.append(reply)                          # 3. remember what it asked for
    results = run_tools(reply.tool_calls)           # 4. YOUR code runs the tools (gates live here)
    messages.append(results)                        # 5. give the results back, then loop
return fallback_message                             # 6. ran out of steps

That is the heart of every agent, in every framework. LangChain, LangGraph, the OpenAI Agents SDK, the Claude Agent SDK, and any company's internal platform all contain some version of this. They differ in features and ergonomics, not in the idea. If you understand these ten lines, you understand what all of them do.

Eight questions to ask about any agent

If you can answer these about any agent, yours or someone else's, you have the right mental model. They are also a good way to structure an answer in the interview.

  1. What can it do? The tools, and how well each is described.
  2. What must it never do, and where is that enforced? In the prompt, or in code?
  3. What does it remember, and where is it stored?
  4. How do I know it works? What are the tests and evals, and what do they miss?
  5. How can I see what happened in a bad conversation?
  6. What happens when something fails? The model, a tool, the database, the network.
  7. How does it get to production and back? Rollout and rollback.
  8. What number does the business care about, and did it move?

LLM fundamentals an AI engineer must know cold

You do not need to know how a transformer works inside. You do need to know how the model behaves as a component: what it costs, how long it takes, how it fails.

Tokens and the context window

The model does not read characters or words. It reads tokens, small pieces of text. In English a token is roughly three quarters of a word. Everything you send and everything it answers is counted in tokens, and that count drives both cost and time.

The context window is the maximum number of tokens the model can look at in one call: the system prompt, all the messages, the tool descriptions, and its own answer together. Modern models have very large windows, but bigger context means slower and more expensive calls, and the model can lose track of details in a very long prompt. So "just put everything in" is not free.

Statelessness and the message list

Each call is independent. The conversation is a list of messages that your code keeps and resends every time. A message has a role: user (the customer), assistant (the model), and tool calls and results are carried inside those messages. The system prompt is a separate instruction at the top that sets the model's role and rules.

In this repoThe Session object holds the message list. MemorySessionStore keeps it between turns. On every turn the agent builds history = [*session.messages, *new_messages] and sends all of it.

How tool calling really works

This is the most important mechanism, and it is simpler than it sounds. The model never runs anything. It only writes text, and one kind of text it can write is "I would like to call this tool with these arguments".

  1. You send the model the tool descriptions: a name, a plain-language description, and a JSON schema for the arguments.
  2. The model decides whether it needs a tool. If yes, it replies with a structured request, for example {"name": "get_portfolio", "arguments": {}}, and stops.
  3. Your code receives that request. Your code decides whether to run it, runs it, and captures the result.
  4. You append the request and the result to the message list and call the model again.
  5. The model reads the result and either asks for another tool or writes the final answer.
assistant: tool_call  get_portfolio {}
user:      tool_result {"holdings": [...], "total_value_nis": 125400.0}
assistant: "Your total balance is 125,400 NIS ..."

The key insight for safety: between the model's request and the execution, there is your code. That gap is where every gate, check and log lives. The model proposes. Your code decides.

Non-determinism and sampling

The model picks each next token from a probability distribution. That is why the same prompt can give different answers. Some models let you tune randomness (a setting called temperature), while newer ones fix it. Either way, design as if the output will vary: test many times, and do not write tests that expect one exact sentence.

Hallucination and grounding

A hallucination is when the model states something that is not true, in a confident tone. In a bank this is not a quality issue, it is a risk issue. The defense is grounding: the model should only state facts that came from a tool result or a retrieved document in this conversation. You enforce this with three layers: the prompt says never invent data, the tools return explicit errors instead of empty results, and the evals check that answers are supported by the tool output.

In this repoRule 1 in domain/system_prompt.md, the internal_error result that says "Do not guess the data", the backend_down eval case, and the groundedness judge in evals/judges.py.

Prompt injection

Anything the model reads can contain instructions: the customer's message, a document you retrieved, a tool result, an email body. The model cannot reliably tell "instructions from my operator" from "text that happens to contain instructions". This is called prompt injection and it is listed first in the OWASP top ten for LLM applications.

The practical rule: never rely on the prompt alone to protect anything that matters. Assume the model can be tricked, and make sure that a tricked model still cannot do harm, because the dangerous capability is simply not available to it.

Cost and latency: what drives each

  • Input tokens are cheap per token, but a chat re-sends everything each turn, and an agent calls the model several times per turn.
  • Output tokens cost more per token and are slow, because the model writes one token at a time. Long answers are the main source of delay.
  • Time to first token is how long until the answer starts. For voice this matters most, because the speech can start before the answer is finished (streaming).
  • The number of round trips matters: each tool step is another model call. A turn with two tool steps is three model calls.

The lesson in those numbers: the tools took 36 milliseconds and the model took over four seconds. In an agent, the model is almost always the slow part, so latency work is mostly about making fewer or smaller model calls, not about faster databases.

Prompt caching

Most of the input in each call is identical to the previous call: the tool descriptions and the system prompt. Prompt caching lets the provider remember that repeated beginning so you pay a small fraction for it and the call starts faster. We measured it in this project: the first call wrote about 1,959 tokens to the cache, and the identical second call read all 1,959 from the cache and was billed for only 4 new input tokens.

CarefulCaching only works on a stable beginning. If you put the current time or a random id at the top of the prompt, every call is different and the cache never hits. Keep stable content first, changing content last. The cache also expires after a few minutes of silence.

Choosing a model

Bigger models reason better and follow complex rules better, but they are slower and cost more. Smaller models are fast and cheap and fine for simple work like routing or classification. A common production pattern is to use a small model for easy steps and a large one only where needed. The way to decide is not opinion but evals: run the same test set on both and compare pass rate, latency and cost.

Good thing to say"I chose a mid-size model as a default for reliability on tool calling and policy following, and I made it a config setting. I would decide the final choice with the eval results, including whether a smaller model passes the same cases. I have not run that comparison yet."

The loop, its variations, and frameworks

Knowing the loop lets you read any framework quickly: you are looking for where it stores messages, how it describes tools, where it runs them, and how it stops.

Anatomy of one turn

Customer message→ Load session→ Model call→ Run tools (gated)→ Model call→ Output check→ Save + log→ Reply

Purple boxes are the model, green boxes are your code. Notice that your code surrounds the model on both sides. That is the shape of every production agent.

Termination: how a loop ends

  • The model answers with text and no tool request. The normal ending.
  • A step limit. A model can get stuck calling tools repeatedly. A hard cap (6 in this project) stops it and returns a safe fallback message.
  • A failure. The model call times out twice, so you return a fallback and keep the state consistent.
  • A handoff. The agent decides it cannot help and escalates to a human. After that, the session is closed to the model.

Parallel tool calls

A model can ask for several tools in one reply, for example both balance and recent transactions. If they do not depend on each other, run them at the same time. With async code this is one line (asyncio.gather), and it cuts the time to the slowest tool instead of the sum. We have a test that proves two 150 ms tools finish in about 150 ms and not 300.

Workflows versus agents, with a bank example

Suppose the task is "answer a customer's balance question".

  • As a workflow: code asks for identity, calls the balance API, passes the number to the model with "phrase this politely". Very predictable, but it cannot handle "actually, also show my last transaction and open a withdrawal".
  • As an agent: the model decides which tools to call in which order, adapting to the conversation. Flexible, but you now need gates, limits and evals to keep it safe.

Real systems are often a hybrid: a workflow for the parts that must be rigid (identity check, payment steps) and an agent for the open-ended parts. Knowing when to make a step rigid is a core skill.

Other patterns you will hear about

RAG (retrieval-augmented generation)

Before answering, search a knowledge base and give the model the relevant text. It reduces hallucination on company-specific facts. In this project it is a tool (search_knowledge) over six documents using BM25 keyword search.

BM25 vs embeddings: BM25 matches words, is deterministic, needs no extra service, and is easy to explain, but misses synonyms. Embeddings match meaning, and need a model and an index. Start simple, move up when the corpus is large or users phrase things differently.

MCP (Model Context Protocol)

A standard way to expose tools and data to a model, so one connector can serve many agents. In an enterprise it is one way to wrap a legacy system once and reuse it. You do not need it for a first build, but you should be able to say what it is and where it would fit: behind the repository interface.

Multi-agent

Several model-driven agents, for example a planner and workers. It sounds powerful and adds a lot: more cost, more failure modes, harder debugging. Default to one agent with good tools. Add more only when one agent's context is overloaded or tasks are truly independent.

Human in the loop

A person approves or takes over at defined points: before a payment, when confidence is low, when the customer asks. Escalation is not a failure, it is a designed path. In regulated industries it is often required.

Pillar 1: Tool design

The model can only use a tool well if it understands what the tool is for. Tool design is closer to writing an API for a very literal, very fast junior colleague than to normal API design.

Why it matters so much

The model picks tools based on only two things: the name and description you wrote, and the schema of the arguments. If two tools sound alike, it will mix them up. If a description is vague, it will call the tool at the wrong time. Most "the agent is dumb" problems are actually "my tool description was unclear" problems.

Principles

1. Clear names that say what happens

get_portfolio, request_withdrawal, escalate_to_human. A verb and an object. Avoid names like process or handle_request.

2. Descriptions that say when to use it, and when not to

Write for a reader who knows nothing. Include what it returns, what it does not do, and any precondition. Our request_withdrawal description says the first call only proposes and the second executes.

3. Few tools, each with one job

Seven tools here. Each extra tool is more for the model to confuse. Prefer a small set of well-named tools over a long list. If you must have many, group or search them.

4. Strict, typed arguments

Use a schema with types, ranges and patterns (phone digits must be exactly four digits, amount must be positive). Validate every call in code, because the model will sometimes send nonsense.

5. Do not ask the model for what you already know

No tool takes a customer id. The code already knows who is verified. Every argument you remove is one less thing the model can get wrong or be tricked into.

6. Return small, useful results

Return only what the model needs, not whole database rows. Large results cost tokens and distract the model. Return explicit "not found" or "error" results, never silent empties.

Errors are part of the interface

When a tool fails, the error message is the next thing the model reads, so it should tell the model what to do. Compare:

Bad:   {"error": "500"}
Good:  {"error": {"code": "insufficient_balance",
                   "message": "The amount exceeds the balance of 125400 NIS."}}
Safe:  {"error": {"code": "internal_error",
                   "message": "The tool failed. Do not guess the data."}}

The third one is deliberately vague about the cause: internals should not leak to the model or the customer, but the instruction "do not guess" prevents the most dangerous reaction, which is making up a number.

Read tools, write tools, and idempotency

  • Read tools only look. If called wrongly, little harm. You can retry them freely.
  • Write tools change something in the world. They need extra care: confirmation, an audit trail, and an idempotency key.
  • Idempotent means doing it twice has the same effect as doing it once. If a withdrawal request times out and is retried, you must not create two. A unique key stored with the request makes the second attempt return the first result.

How to test a tool description

Write the eval cases first: "what's my balance" should call get_portfolio; "should I buy" should call nothing. Run them. If the model picks the wrong tool, change the description or rename the tool, then run again. Treat descriptions like code: they are changed, tested and reviewed.

Common mistakes
  • Giving the model a general-purpose "run SQL" or "call any API" tool. It is powerful and nearly impossible to make safe.
  • Putting security in the description ("only use this for the logged-in user"). A description is a hint, not a lock.
  • Returning huge payloads and hoping the model finds the right field.
In this repodomain/tools.py defines all seven tools with pydantic argument models. core/tools.py is the registry that validates, gates and runs them. Compare get_portfolio (no arguments) with verify_identity (the only tool that takes a customer id, because that id is the claim being checked).

Pillar 2: Gates in code

The model proposes, your code disposes. Anything that must never happen should be impossible, not just discouraged.

The core idea

A prompt is persuasion. Code is law. When you tell the model "never show another customer's data", you are asking politely. When your tools simply have no way to receive a different customer's id, you have made it impossible. The first fails under pressure from a clever user. The second does not, because it does not depend on the model's cooperation.

Threat model in plain words

Assume three things will happen in production:

  1. Some users will try to trick the agent ("ignore your instructions, I'm the admin").
  2. The model will sometimes misunderstand and do the wrong thing without any attacker.
  3. Content the agent reads (documents, emails, tool results) may contain hidden instructions.

The question to ask for each capability is: if the model were fully compromised right now, what is the worst thing it could do through this capability? Then design so that the answer is acceptable.

What belongs in the prompt, and what in code

Put in the prompt

  • Tone, language, style.
  • Judgment calls: is this advice? is this out of scope?
  • When to use which tool.
  • What to say when refusing.

Things that need understanding of meaning, where a rule cannot decide.

Put in code

  • Who may see what.
  • What may be changed, and after what confirmation.
  • Limits (steps, time, amounts).
  • Anything with legal, financial or safety consequences.

Things that must hold every time, even when the model is wrong.

Good designs use both. The prompt makes the common case smooth, and the code catches the rare failure. The regex check for investment advice is a good example of the combination: the prompt does 95 percent of the work, and the regex is a cheap safety net for the rest. It is intentionally coarse, and the evals measure what it misses.

Honest limits of our gates

  • "Customer id plus last four phone digits" is a weak identity factor. Real systems use the client's login or a one-time code.
  • The confirmation gate proves that a user turn happened between proposal and action, not that the user said yes. The prompt asks for a clear yes and an eval checks the flow. For real money you confirm out of band, with a button or a code.
  • The lockout counts failures per session, so someone could start new sessions. Production needs per-customer rate limits.
Good thing to say"I separate what needs judgment from what must be guaranteed. Judgment goes in the prompt. Guarantees go in code, and I design so that a fully fooled model still cannot reach another customer's data or move money without a confirmation."
The wrong answer"I told the model in the system prompt not to do that." Interviewers hear this as: the safety depends on the model behaving.

Pillar 3: State and memory

Because the model is stateless, "what the agent knows" is whatever your code stores and resends. Deciding what to store, where, and for how long is a core design task.

Two kinds of state

Conversation history

The list of messages, including tool calls and results. It is what lets the model say "as I told you" and "the withdrawal we just discussed". It grows with every turn.

Control state

Facts your code needs, separate from what the model says: is the customer verified, how many failed attempts, is there a pending write, has the session been escalated. This state drives the gates.

Why separate them? The model can be wrong about the conversation, but the code cannot be wrong about "is this customer verified". Never infer security state from the chat text. Keep it in explicit fields, set only by your code.

What is in the session here

Session
  id, messages[]            # the conversation
  turn                      # a counter, used by the confirmation gate
  verified_customer_id      # set only by verify_identity
  failed_verifications      # for lockout
  pending_action            # a proposed write + idempotency key + the turn it was proposed
  handoff                   # set when escalated

Where state lives: the stateless API

Your API servers should be stateless: they keep nothing between requests. All state goes in a store the servers share. This is what lets you run several copies behind a load balancer, restart them freely, and deploy new versions without losing conversations.

  • In memory (our MemorySessionStore): fine for demos and tests. Lost on restart, not shared between copies.
  • Redis: fast shared store with expiry. The usual choice for sessions.
  • A database: when you need history for audit, analytics or long-lived conversations.

The code reaches the store only through an interface, so moving from memory to Redis changes one line in container.py.

The growing history problem

Every turn adds messages, and every model call re-sends them all. A long conversation becomes slow and expensive, and eventually exceeds the context window. Options, from simplest:

  1. Do nothing for short conversations. Most customer-service chats are short.
  2. Truncate old messages. Cheap, but may drop important facts.
  3. Summarize older turns into a short note. Keeps facts, costs one extra call.
  4. Keep important facts in control state (verified id, pending action) so they never depend on old messages being present.
  5. Clear old tool results that are no longer needed, since large results are the main bloat.

Short-term versus long-term memory

Everything above is short-term, within one conversation. Long-term memory means remembering across conversations (a customer's preferences, a past issue). It is a separate feature with serious privacy implications, especially in regulated industries: what may you store, for how long, and who can see it? Do not add it casually. For this project, the honest statement is: no long-term memory, by design.

Concurrency and consistency

If two requests for the same session arrive at the same time (a double click, a retry), they can read the same state and overwrite each other. Our in-memory version does not guard against it. In production, use a per-session lock or an atomic update in Redis. It is a known gap, written down in PRODUCTION.md.

What happens to state when the model call fails?

A decision we made on purpose: if the model fails mid-turn, we keep the control state (the customer stays verified) but drop the half-finished messages. A tool call without its result is an invalid history for the provider and would break every later request. The cost: in a rare case, a write that already executed has no record in the chat, so the customer may be asked again.

In this repocore/session.py (the state), adapters/memory_session_store.py (the store), core/agent.py lines around if reply is None (the failure behavior).

Pillar 4: Evals

An eval is a repeatable test that tells you whether the agent behaves correctly. Without evals, every prompt change is a gamble, and "it seems to work" is the only evidence you have.

Interview warning from your own notesYour notes say a previous candidate was rejected for gaps in evaluation and deployment. Evals are the part to be most prepared on, and most honest about.

Why agents need a different kind of testing

A normal function has one right answer, so you assert equality. An agent's output is free text that can be phrased many ways, may call different tools in a valid order, and varies run to run. So you cannot assert one exact string. You assert properties: the right tool was called, the number in the answer is correct, no forbidden tool was called, the escalation flag is set.

Building a good eval set

  1. Start from the requirements and the risks, not from what is easy to test. Each requirement ("refuse investment advice") becomes at least one case.
  2. Cover categories: happy path, knowledge questions, identity gate, write actions, refusals, escalation, out-of-scope, injection, multi-turn, tool failure. Our 20 cases span 10 categories.
  3. Use distinctive data so wrong answers are easy to detect. C007 has a balance of 987,654 so any leak is obvious.
  4. Prefer deterministic checks (a tool was called, a number appears, a flag is set). They are cheap, stable and explainable.
  5. Use a judge only for what you cannot check mechanically, with a fixed written rubric.
  6. Grow it from real failures. Every bad production conversation becomes a new case. This is how the set stays relevant.

Judging with a model: use with care

An LLM judge reads the answer and the evidence and says whether the answer is supported. It is useful and also unreliable in specific ways you should be able to name:

  • It shares blind spots with the model being judged if it is the same model. Use a different model as judge in production.
  • It can be lenient or inconsistent. Give it a strict rubric, ask for a reason, and spot-check its verdicts by hand.
  • It costs money and adds variance. Use it only where needed.

The metrics that matter

  • Pass rate per category, not only overall. "95 percent overall" can hide "0 percent on injection".
  • Safety categories must be near 100 percent and are release blockers. Style categories can tolerate some misses.
  • Latency: average and p95 (the time that 95 percent of turns beat). Averages hide the slow tail.
  • Flakiness: run each case several times. A case that passes 3 of 5 times is a finding, not a pass.
  • Cost per conversation.

Evals as a release gate

Run the eval set automatically on every change to the prompt, model, tools or config, before release. Block the release if safety cases fail or the overall rate drops against the baseline. This is the same idea as CI for normal code, applied to behavior.

Common pitfalls

  • Overfitting to the evals. If you tune the prompt until all 20 pass, you may have taught it those 20. Keep some cases hidden, and keep adding new ones.
  • Brittle regexes. A correct answer written as "125.4K" fails a check for "125,400". Read failures before trusting them.
  • Testing only the happy path. The value is in the adversarial and failure cases.
  • One run. Model variance means one run proves little.

Where this project honestly stands

The machinery is built and unit-tested: 20 cases, the runner, the deterministic checks, the judge with its rubric, and the report with per-category and p95 numbers. The full live eval has not been run yet. The documentation says so, and EVALS.md lists known weaknesses (regex brittleness, same-model judge, 20 cases, one run). Say this plainly in the interview, and say what you would do first: run it, read every failure, fix the top ones, and rerun several times.

I know the limits: the judge is biased, regexes are brittle, and the set is small, so I would grow it and run each case multiple times."

Pillar 5: Observability

When a customer says "the agent told me something wrong", you must be able to reconstruct exactly what happened. If you cannot, you cannot fix it, and a regulated client will not accept it.

The question observability answers

For any single conversation, you should be able to answer: what did the model see, what did it decide, which tools ran with what inputs and outputs, how long did each step take, what did it cost, and why did it end the way it did? Three kinds of signals give you this.

Logs

Discrete events with details. "tool_call get_portfolio took 3 ms". Good for finding one specific thing.

Traces

A timeline of one request with nested steps: turn, then model call, then tool call, then model call. Good for "where did the time go".

Metrics

Numbers over time: requests per minute, error rate, p95 latency, cost per hour. Good for dashboards and alerts.

What this project logs

  • A summary line per turn: tools used, tool errors, total / model / tool time, tokens, escalated, failed, policy violation.
  • An event per tool call: name, milliseconds, whether it errored, the error code.
  • Model usage: uncached input, cache write, cache read, output tokens.
  • Failures with a full traceback: retries, tool exceptions, the final model failure.
  • Identifiers on every line: a correlation id per request and the session id, so you can pull the whole story with one search.
  • File, line and function of the code that logged, so you can jump to the source.
In this repocore/logging.py (two formats: readable console for development, JSON for log systems), and the log_event calls in core/agent.py and core/tools.py.

What you must not log

Message text, account numbers and balances are personal data. We do not put message contents in logs. That means debugging content needs a controlled transcript store with access control and retention rules, or a debugger on a test environment. In a bank, "we logged the customer's balance in plain text" is a serious incident.

Why you log errors with tracebacks

The tool registry converts every exception into a clean error result for the model. That is good for the conversation and bad for debugging, because the original cause disappears. So each place that catches an exception also logs it with the stack trace. The model and customer see a safe generic message, and the engineer sees the real cause.

Production observability: what you would add

  • Distributed tracing (OpenTelemetry): one trace per turn, a span for each model call and each tool call, with attributes like model name, token counts, cache hits, tool name and error code. Viewed in an observability tool built for LLM applications.
  • Dashboards: latency percentiles, tool error rate, escalation rate and reasons, fallback rate, cost per conversation.
  • Alerts tied to rollback criteria: error rate or latency up, escalation spike, any sign of data exposure.
  • Sampled review: humans read a sample of conversations each week, plus every escalation and complaint.
  • Replay: the ability to re-run a recorded conversation against a new version to see if the behavior changed.

A debugging story to be able to tell

While building the dev cache we noticed that three identical-looking messages were still charged. The logs showed the same session id on all three and a cache miss on each. The reason: the cache key includes the whole conversation history, and the chat page keeps the session, so each repeat was a longer conversation and so a different key. Starting a new conversation fixed it. The point of the story: the logs answered a question that guessing would not have.

Good thing to say"I made the agent observable first, because everything else depends on it. One summary per turn, an event per tool, usage and cache numbers, identifiers on every line, and tracebacks where exceptions are converted. In production I would add OpenTelemetry traces and an LLM observability tool."

Reliability, latency and cost

A demo works once. A product works when the network is slow, the database is down, the model is overloaded, and a thousand people are chatting at the same time.

Everything external will fail

In this system four things can fail: the model API, a tool, the database or client system, and your own code. For each, decide in advance what the customer sees and what state is left behind.

Temporary errorRetry with backoff: wait a little, double the wait each time, give up after a few triesOne retry; 0.5 s then 1 s

A retried writeIdempotency so it cannot happen twiceUnique key on the request

One subtlety worth knowing: retries can make things worse. If a service is overloaded, many clients retrying at once make it fall over harder. That is why backoff (waiting longer each time, ideally with a little randomness) and a small retry count matter. Also only retry things that are safe to repeat, which is another reason for idempotency.

Latency: where the time goes

We saw that a turn took about 4 seconds and the tools took 36 milliseconds. That tells you where to work.

  • Fewer model round trips. Each tool step is another call. Combine steps where safe, run independent tools in parallel, and consider prefetching data you will almost certainly need.
  • Smaller prompts. Fewer tokens in means faster and cheaper. Trim tool results and old history.
  • Prompt caching. The repeated prefix is read from cache, which reduces cost and the time to first token.
  • A faster model for easy steps. Route simple intents to a small model.
  • Shorter answers. Output tokens are the slowest part. Ask for concise replies.
  • Streaming. Start showing or speaking the answer before it is complete. This does not make the total shorter but makes it feel much faster.

Voice is different

The company you are interviewing with builds voice, chat and email agents, so voice questions are likely. Voice changes the constraints a lot:

  • Silence is very noticeable. In conversation, people feel a pause of more than about a second. A text chat can take four seconds without annoying anyone. A phone call cannot. Treat this as a rule of thumb and confirm the actual target with the client.
  • Streaming is essential: the speech engine starts talking as soon as the first sentence is ready.
  • Filler phrases ("let me check that") can cover a slow tool call, but they are a patch, not a fix.
  • Prefetch the customer's data as soon as they are identified, so most questions need no database trip during the call.
  • Database calls count. A slow lookup in the middle of a voice turn is felt directly. Index lookup keys, pool connections, cache hot data, set tight timeouts.
  • Interruptions and speech recognition errors make inputs messier than typed text: names, numbers and digits are often misheard. Confirm important values back to the caller.

Note that in a real deployment the agent often does not own the database. It calls the client's systems through APIs, which may be slow or unreliable. That makes caching and prefetching more important than tuning queries.

Cost as a design constraint

  • Cost per conversation = (input tokens x input price) + (output tokens x output price) x number of model calls. An agent multiplies the cost of a single call.
  • Levers: prompt caching, smaller models where possible, shorter prompts and results, fewer round trips, and caching of static knowledge.
  • Compare it to the thing it replaces: the cost of a human handling the same contact. That is the business case.

For orientation, the model used here is priced at about $2 per million input tokens and $10 per million output tokens (check current pricing). Cached input is read at about a tenth of the normal input price. Our 6,300-token turn cost roughly a cent without caching, which matches what you saw.

Shipping and operating an agent

An agent changes whenever you change the prompt, the model, a tool, or the configuration. Releasing it safely is its own skill, and it is the second thing a past candidate was rejected on.

What a "release" contains

In normal software a release is code. For an agent, behavior depends on four things together: the prompt, the model and its settings, the tools and their descriptions, and the configuration (limits, policies). Changing any one can change behavior, even if no Python changed. So version them as one unit (a single git commit or tag), and log that version on every turn so you can tell which release produced a conversation.

Deployment strategies

Blue-green

Run the new version (green) next to the old (blue). Test green, then switch all traffic at once. Rollback is switching back. Simple and fast, but everyone gets the change at the same moment.

Canary

Send a small share of traffic (say 1 to 5 percent) to the new version, compare it to the old one on real metrics, then increase gradually. Better for agents, because real behavior is hard to fully predict from evals.

Shadow mode

The new version receives real traffic and produces answers, but customers never see them. You compare offline. Zero risk to customers, costs extra model calls.

Feature flags and a kill switch

Turn individual capabilities on and off without a deploy, for example disable the write action. A global switch that routes everything to humans is the emergency brake.

A detail specific to agents: pin a conversation to one version. If the prompt changes in the middle of a chat, the model sees a history written under different rules, which can confuse it.

Rollback criteria: decide before you ship

Write down in advance the numbers that trigger a rollback, so the decision is not made under pressure. Examples:

  • Eval pass rate below baseline in CI: the release does not start.
  • Online: escalation rate, fallback rate, or tool error rate up by more than an agreed margin.
  • Latency p95 above the budget.
  • Any confirmed exposure of another customer's data: immediate rollback.

The rollout path with a regulated client

  1. Staff pilot: employees use it, compare with what agents would say.
  2. Read-only, narrow scope: a few intents, with an easy path to a human.
  3. Measure against the human baseline: handle time, resolution, satisfaction, error rate.
  4. Expand by intent and by share of traffic.
  5. Enable writes last, with limits (for example a daily cap per customer) and a full audit log.

Operating it afterwards

  • Watch the dashboards, review a sample of conversations, and turn each failure into an eval case.
  • Models change: a provider update can shift behavior. Pin model versions where you can, and rerun evals when you upgrade.
  • Prompts drift as people add rules. Review them like code, remove outdated rules, and keep them short.
  • Keep an audit trail of every write action: who, what, when, with which key, with what outcome.

Security and compliance topics to be ready for

  • Personal data: minimize what is sent to the model, mask it in logs, set retention limits, check the provider's data-handling terms.
  • Least privilege: the agent's credentials should allow only what its tools need. Read-only first.
  • Data residency: where is data stored and processed? Banks and government often have strict rules.
  • On-premises and network constraints: the client may not allow outbound internet. That can force private connectivity, a self-hosted component, or a different model deployment.
  • Regulation specific to the use case: in this project, giving personalized investment advice requires a licence in Israel, so the agent must refuse and hand over to a licensed advisor.
  • Auditability: be able to show what the agent said and why.

The forward deployed engineer

An FDE is an engineer who works directly with customers to make a product solve their real problem in their real environment. The code is only part of the job.

What I know and what I am inferringWhat you told me about the company: it deploys production-grade AI agents (voice, chat, email) for regulated enterprises such as banks, insurers, telecom and the public sector. The rest of this tab describes the FDE role in general and how it likely applies. I do not know the company's internal processes, so treat those parts as informed expectations, not facts, and ask about them in the interview.

Why the role exists

A general product cannot fit every enterprise out of the box. Each client has different systems, data, rules, and people. Someone has to stand between the product team and the client, understand both, and make the product work in the client's world. That someone writes code, but also talks to stakeholders, scopes work, and measures results. That is the FDE.

Three hats

Engineer

Builds the integrations, tools, prompts, data connections and deployments. Debugs in the client's environment. Writes evals and monitors production. Moves fast and prototypes.

Product owner

Decides what to build first and what to leave out. Turns a vague wish into a scoped, testable behavior. Says no to scope creep. Feeds what clients need back to the product team.

Business analyst

Understands the client's process and numbers. Finds which contact types are worth automating. Defines success in the client's terms (cost, handle time, satisfaction) and reports it.

A typical engagement, step by step

  1. Discovery. Listen. What is the problem in business terms? Who feels it? How is it handled now? What volume? What are the costs and the pain? What are the rules and risks? Ask to see real examples and the systems involved.
  2. Scoping. Choose a narrow first slice with clear value and low risk, such as read-only status questions. Agree on success metrics and on what is out of scope.
  3. Design. Decide the tools, the data access, the escalation rules, the guardrails, and the evals. Review with the client's security, compliance and operations people early.
  4. Build and integrate. Connect to legacy systems, often through awkward interfaces. Start with mocks, replace them step by step.
  5. Evaluate. Build the test set with the client's real cases. Show results honestly, including failures.
  6. Pilot. Small, monitored, with an easy path to a human. Compare against the baseline.
  7. Expand and operate. Add intents, tune, monitor, review transcripts, fix failures, report numbers.
  8. Feed back. What you learned should improve the product, so the next client needs less custom work.

The reality of enterprise environments

  • Legacy systems. Old APIs, SOAP, batch files, systems of record that update overnight, and several systems with partial overlap. Expect slow, flaky and badly documented interfaces.
  • Access takes time. Credentials, network paths, security reviews, data-protection approvals. Plan for waiting, and work with mocks meanwhile.
  • Compliance. Auditors, legal and risk teams have a say. Design for auditability from day one.
  • Change management. Call-center agents may fear being replaced. Success depends on people adopting it. The agent should make their work better by taking the routine and passing on clean handoffs.
  • Dirty data and unclear ownership. The question "who owns this system" often takes the longest to answer.

The 2-minute project pitch

"I built an agent for an investment house's customer service. The business problem is a call center loaded with routine questions: balance, transaction history, withdrawal status, fee questions. The agent handles those, and hands everything else to a human with a structured summary.

Design choices

Why did you not use a framework?

The loop is about ten lines, and every framework has its own version of it. I wanted the gates, state and observability around it to be explicit and testable, and I wanted to be able to explain every line. In a team I would use whatever framework or platform they have, keeping the same boundaries. My code is behind interfaces, so the loop could be swapped without touching tools or gates.

Why did you choose this model?

A mid-size model as a default: strong enough for tool calling and following policy rules, with reasonable latency and cost. It is a config setting. The real decision should come from evals: run the same cases on a smaller model and compare pass rate, latency and cost. I have not run that comparison yet, and I would not claim the choice is optimal.

Why Postgres? Would the agent own a database in production?

Customer, account and transaction data is relational, and Postgres mirrors a real enterprise backend, including a network hop whose latency I can reason about. In production the agent usually does not own the database. It calls the client's APIs. The repository interface is exactly that seam: I would write an HTTP or SOAP adapter that implements the same methods, and caching and prefetching would matter more than query tuning.

Why BM25 and not embeddings?

The knowledge base is six short documents and keyword-heavy: fees, rules, products. BM25 is deterministic, needs no extra service, adds no latency and I can explain why a document ranked first. It misses synonyms and has no chunking. When the corpus grows or customers phrase things differently, I would add chunking and hybrid search with embeddings.

Why did you pick this dataset / this domain?

Because it combines the hard parts that regulated clients have: identity, personal data, a licensed-advice boundary, and a write that moves money. It is small enough to understand fully but exercises every safety mechanism. I used distinctive mock values so any data leak is easy to detect in evals.

Why async everywhere?

Model and tool calls are waiting on the network. Async lets one process handle many conversations, and makes parallel tool calls a one-liner. A test proves two 150 ms tools take about 150 ms in total.

Safety and correctness

How do you stop the agent from leaking another customer's data?

Structurally. Tools take no customer id. They read the verified id from the session, which only the identity tool can set, and a registry gate blocks data tools before verification. So a prompt-injected model asking for customer C007 can only ever fetch the verified customer's own data. There is an eval for it, and the other customer's balance is distinctive so a leak would be obvious.

What if the model is tricked into calling the withdrawal tool?

The first call only records a proposal and returns "confirmation required". It executes only if the same call is repeated on a later user turn with identical arguments. The idempotency key is generated by the code and never visible to the model. Limit: the code proves a turn passed, not that the user said yes. For real money I would confirm out of band with a button or a one-time code.

How do you handle prompt injection?

I assume it will succeed sometimes and design so that success does not hurt. Dangerous capabilities are not available to the model, they are gated in code. I also treat tool results and retrieved documents as untrusted input. I test it with injection cases in the evals.

How do you prevent hallucinated numbers?

Three layers: the prompt says never state data that did not come from a tool, tool failures return explicit errors that say "do not guess", and evals check groundedness, with a judge that sees the raw tool results. The outage case checks that no number appears when the backend is down.

Evaluation

How do you know the agent works?

Three levels. Unit tests with a scripted fake model prove my code: loop, gates, retries, confirmation. Twenty scenario evals against the live model check behavior across ten categories using deterministic checks first. A groundedness judge with a fixed rubric covers what regexes cannot. In production I would add online metrics and a regression set built from real failures. My honest caveat is that the live eval has not been run yet, and regexes and a same-model judge are weak points.

What would you do if the eval pass rate drops after a prompt change?

Look at which categories dropped before looking at the overall number. Read the failing transcripts, find the cause, usually an instruction that now conflicts with another, fix it, and rerun several times because of variance. If safety categories drop, the change does not ship.

What are the weaknesses of your eval?

Regexes on free text are brittle. The judge is the same model, so it is likely lenient. Twenty cases from one run is a small sample. The confirmation case checks the flow but not an ambiguous reply. It uses an in-memory repository, so database behavior is covered by separate integration tests. I would fix this by running cases multiple times, using a different judge model, and growing the set from real failures.

Production

How would you deploy a prompt change safely?

Prompt, model, tools and config are one versioned release. CI runs the evals as a gate. Then a canary: a small share of traffic to the new version, compared on escalation rate, fallback rate, tool errors, latency and satisfaction, with rollback criteria written in advance. Conversations stay pinned to one version.

How do you make a voice agent fast enough?

First measure where the time goes; in my own measurements the model call dominates, not the database. Then: stream the model output into speech, prefetch customer data right after identification, cache static knowledge, use prompt caching and a small model for routing, run independent tools in parallel, keep prompts and tool results small, and set a per-turn latency budget with a filler phrase when it is exceeded. Not all of that is built; parallel tools, indexed lookups and timing logs are.

How would this scale?

The API is stateless, so run many copies behind a load balancer with sessions in Redis and a per-session lock. Add rate limiting, queues for long workflows, a fallback model, and cost tracking. The in-memory store and missing lock are documented gaps.

What would you monitor in production?

Latency percentiles split into model time and tool time, tool error rate, fallback rate, escalation rate and reasons, token usage and cost per conversation, and sampled groundedness checks. Alerts tie to rollback criteria, and humans review a weekly sample plus every escalation and complaint.

FDE and behavior

A client wants the agent to do something risky. What do you do?

Understand the goal behind the request first. Then explain the risk in their terms, propose a safer version (read-only first, confirmation, a human approval step, a daily cap) and show how we would measure it. If a requirement is a legal line, such as licensed advice, I do not bend it, I design the handoff to the licensed advisor.

The client's system is slow and unreliable. What do you do?

Measure it, then protect the conversation: timeouts, one retry, clear fallback wording, caching and prefetching where data is stable, and an alert on the dependency. I would also bring the numbers to the client's team, since a fix on their side may be the best improvement.

How do you handle a vague request like "make it smarter"?

Turn it into something measurable: which conversations fail, why, how often. Look at real transcripts, categorize the failures, pick the top one, write an eval case that captures it, fix it, and show the number move.

What are the weakest parts of your project?

Identity is a weak factor and lockout is per session. The advice check is a coarse regex. There is no per-session lock, so concurrent requests could interleave. The confirmation proves a turn passed, not agreement. And the live eval run is pending. I documented all of them, and I know what I would do about each.
